# Support Bridge project guidance

Start with our customer problem, `docs/ASSUMPTIONS.md` and `docs/GOVERNANCE.md`. Support Bridge is our headless escalation workflow for explicitly linked GitHub issues and Zendesk tickets. Keep documentation in our product voice: describe our decisions, implementation, evidence and operating limits directly. Keep private discussions and unrelated material outside the repository.

Use product-focused branch names under `feature/`, `fix/`, `chore/`, `docs/` or `ci/`, and the configured maintainer identity for commits. Keep assistant/tool branding out of repository text, branch names and commit metadata. Keep the generic AI-use disclosure honest. GitHub Actions is our CI; changes go through pull requests and its named required-check gate. A workflow passing does not itself prove that server-side branch protection is enabled.

Review this file at the start and close of every task. Update it in the same change when architecture, operating rules, verification requirements or lasting project decisions change. Link the detailed guides instead of copying them here. Keep task history, temporary readings, credentials and private deployment settings outside this file.

- Keep plain PHP, shared CLI/API application logic, and pure merge/retry/governance policies. Add adaptive behavior only for a demonstrated need; keep deterministic execution free of runtime model decisions.
- Follow the PSR-4 namespace/path mapping and the checked-in PSR-12 ruleset. Keep entry scripts thin, use focused objects with constructor dependencies, and run the style gate alongside behavior checks. Add patterns where they clarify ownership or isolate a use case; avoid global service lookup and classes that only rename a function.
- Keep application commands and queries separate with typed messages and explicit handlers shared by CLI and HTTP. Queries must not construct providers or execute reconciliation. This synchronous CQRS boundary uses one SQLite store; it does not add a queue, event sourcing or a separate read database.
- Reuse the explicitly injected business connection within its application context. Keep connection configuration, schema upgrades, transaction handling and canonical locking in persistence infrastructure. Do not introduce a process-global database Singleton or change saved plan JSON while restructuring classes. Keep Composer style tooling in development/verification, outside the runtime image.
- Never rely on AI in compliance. AI output cannot decide policy satisfaction, authorize a write, choose a conflicting source or supply operator approval. Document policy ownership and missing controls explicitly.
- Preserve the review boundary: title-only plans use the explicit link's opt-in; any outbound state change holds the whole plan for explicit approval. Approval binds pair, exact durable plan and governance policy version, is checked against fresh evidence, and cannot be granted by retry or source resolution.
- Keep durable target/preimages/versions, unknown-outcome read-before-retry, no baseline advance until verified convergence, and the canonical single-worker lock. Existing pending work must survive upgrades and receive the current gate.
- Treat the shared operator token as broad authority. Do not claim verified human identity, individual attribution, scoped agent credentials or separation of duties. The business review skill is read-only guidance; its Markdown allowlist does not enforce privileges.
- Update CLI, API/OpenAPI, metrics, tests and docs together when state/behavior changes. Audit failures must prevent subsequent effects; best-effort telemetry must not decide business correctness. Report actual test evidence separately from customer/vendor/production validation.
- Keep Compose defaults local and host ports on loopback. Preserve separate credential volumes, the shared single-host state/lock and non-root read-only runtime. Run the isolated verification, actual stack smoke and disposable lifecycle checks in `docs/DOCKER.md` for container changes; never remove the normal stack's volumes as routine cleanup.
- Use explicit `-p support-bridge-traffic` and both Compose files for traffic operations, as documented in [TRAFFIC.md](docs/TRAFFIC.md). Preserve its separate volumes, local-only checks, owned-record markers, bounded pair pool and generator lock. Source edits and record-targeted faults use the canonical application lock; release it before HTTP calls. Run `tests/traffic.php` and the disposable traffic check when changing this behavior.
- Scripted review belongs only to the isolated synthetic workload. Keep its visible review delay, normal exact-plan approval API, freshness checks and persisted retry schedule. The deterministic test driver is not an advisory AI agent or a verified human approver. Never rewrite pending work or approval evidence to make a demonstration progress.
- Treat Grafana credential files as bootstrap inputs, not proof of the current account after rotation. Verify the intended stack and port, then the actual browser login before claiming a login fix. The standard smoke check assumes the bootstrap account; report that limitation for rotated deployments without resetting their accounts or volumes. See [Docker operation](docs/DOCKER.md).
- Keep available Dependabot proposals visible, including newer runtime lines. A package advisory's fixed version does not establish an available or repaired parent image. Follow [CI policy](docs/CI.md) and [security maintenance](SECURITY.md) for reviewed adoption, scanner coverage and bounded asset repair. Check results against the current commit and confirm fresh status/logs before cancelling or retrying CI.
- Preserve explicit architecture, trade-off, limitation and AI-use sections. Keep the AI disclosure honest and focused on how we develop the product. Keep private materials, credentials and runtime state outside source. Existing authorization governs external actions; this guidance supplies no blanket deployment permission.
