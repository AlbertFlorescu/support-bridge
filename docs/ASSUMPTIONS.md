# Explicit assumptions register

Each row states an assumption or design decision, its consequences and the check it needs. Customer discovery, live vendor validation and production capacity measurements remain outstanding.

The [governance guide](GOVERNANCE.md) defines write controls, policy ownership and rollout responsibilities.

## Customer, value and domain

| ID | Assumption or explicit decision | Why it matters; consequence if wrong | Validation or enforcement |
| --- | --- | --- | --- |
| A01 | We target B2B SaaS teams that use Zendesk Support and GitHub Issues for the same escalations. | Demand remains a hypothesis. Teams with different tools or escalation models may need different adapters and ownership rules. | Discuss current escalation work with support and engineering before a pilot. |
| A02 | The same escalation already has one ticket and one issue, and an operator knows the correct mapping. | The service does not infer identity, create records or attach several tickets to one issue. Duplicate mappings are rejected. | Explicit `link`; database uniqueness on each remote ID. |
| A03 | Copying summaries and resolution updates is repetitive, and stale copies create avoidable follow-up. | Less copying and fewer stale escalations are expected value, not measured outcomes. No invented time savings or revenue figures are claimed. | Measure copying actions/minutes and stale-pair frequency before/after an opt-in pilot. |
| A04 | Both teams may correct the summary and reopen/resolve the escalation. Neither is globally authoritative. | Two-way sync creates conflicts. A single authoritative source would simplify the workflow if both teams accept it. | Three-way field merge; validate field ownership with the operating team. |
| A05 | Synchronizing only title/subject and binary resolution state is a useful complete slice. | Comments, descriptions, assignee updates, priority, requester details, attachments, deletion and GitHub closure reasons do not cross the boundary. | `Record` plus provider patch allowlists and contract tests. |
| A06 | A nonempty title of at most 500 UTF-8 bytes is sufficient for this slice. | Valid vendor records outside this subset stop visibly instead of truncating or corrupting data. JSON Schema describes the byte rule; PHP enforces it. | `Record` validation; no implicit transliteration or truncation. |
| A07 | Zendesk new/open/pending/hold all mean canonical open; solved/closed mean canonical closed. | The model is intentionally lossy. Custom statuses and business rules may not fit. A title-only update must preserve the original workflow state. | Adapter mapping tests; account-specific sandbox validation still required. |
| A08 | A GitHub closed transition should mark Zendesk solved, not irreversibly closed. A solved ticket may reopen; a closed ticket cannot be edited. | No follow-up ticket is automatically created. A required mutation to an immutable ticket becomes dead work. | Zendesk writable flag and preflight; operator chooses a suitable existing follow-up link separately. |
| A09 | Only escalations whose subjects are appropriate for the private engineering repository are opted in. | Subjects can contain confidential or personal data even though comments/requester details are excluded. The program does not redact title text or verify repository visibility. | Human opt-in and sandbox records; privacy review before real traffic. |

## Reconciliation and failure model

| ID | Assumption or explicit decision | Why it matters; consequence if wrong | Validation or enforcement |
| --- | --- | --- | --- |
| A10 | Current canonical fields and a durable common baseline are enough to detect ordinary one-sided changes. | Timestamps are not used to select the most recent winner. Values changed and reverted between observations can be unobservable. | Pure merge-policy tests; observable version changes checked on pending work. |
| A11 | First-seen differences and divergent same-field edits require an operator decision. | No source is silently preferred, and one conflict suspends the entire pair. Safe fields may be delayed. | Conflict snapshots, typed state errors and freshness checks. |
| A12 | API version timestamps are useful observation guards, but their granularity is finite. | Equal timestamps do not prove no intervening edit. GitHub does not document atomic conditional issue writes; its GET→PATCH race can still overwrite an edit. | Documented limitation; minimal patches, preflight and verification reduce risk without promising complete prevention. |
| A13 | A remote write can commit before its response is lost or before local state is updated. | Retrying a stale patch blindly could overwrite a newer edit. Local SQLite cannot provide a transaction across both vendors. | Durable target/preimages/versions; read-before-recovery; partial-success and timeout tests. |
| A14 | A pending destination that still needs a write must retain its recorded version. | Even unrelated destination changes can require manual review. A destination already at the full target can be acknowledged without writing. | Conservative recovery guard and edit-and-revert tests. |
| A15 | Five failed attempts, exponential delay, bounded jitter and vendor retry guidance are a reasonable prototype policy. | This is not a customer-approved outage budget. Dead work needs operator intervention; automatic recovery does not continue forever. | Pure retry policy; persisted attempt/next-run fields. |
| A16 | No remote create operation is needed. | Updates can be reconciled by reading values; duplicate remote creation and create-idempotency protocols are outside scope. Repeated operator commands may return a state conflict. | No create API in provider interface; unique links. |
| A17 | An operator is available to resolve conflicts and correct permanent failures. | No escalation owner, staffed on-call process or notification destination has been agreed. | `status`, `inspect`, `resolve`, `retry`; choose ownership before deployment. |

## Workload, persistence and deployment

| ID | Assumption or explicit decision | Why it matters; consequence if wrong | Validation or enforcement |
| --- | --- | --- | --- |
| A18 | We currently support a low-volume, single-team pilot with a small opt-in link set. We have not established throughput, latency or availability targets. | Production capacity is unmeasured. A synchronous sweep and full in-memory link enumeration become bottlenecks as volume grows. | Measure provider latency, calls/change, convergence lag and unresolved age before expanding usage. |
| A19 | One process at a time operates on one canonical SQLite database on a local filesystem. | A file lock is not a distributed lock; shared network storage, multiple hosts and horizontal workers are unsupported. | Nonblocking lock, canonical paths and lock-release tests. |
| A20 | The host filesystem and SQLite durability semantics provide the expected local persistence. | Disk failure, corruption, full disks and restored inconsistent snapshots can still lose state. WAL files matter during backup. | WAL + synchronous FULL; backup with SQLite tooling or stop the worker before copying. No tested disaster-recovery claim. |
| A21 | One database belongs to one GitHub repository, Zendesk tenant and local/live mode. | Environment changes must not redirect old numeric links and baselines to another account. Renaming/moving repositories needs an explicit migration. | Persisted identity binding; mismatches refuse reuse. |
| A22 | We invoke bounded sweeps nominally once per minute, using the Compose worker loop or an external timer for native deployment. | Actual retry execution is at or after `next_run`, delayed by scheduler cadence and sweep duration. Polling is not instant delivery. | Persisted schedule and a single canonical database lock. The container loop waits between sweeps and handles termination; its heartbeat is not a convergence SLO. |
| A23 | PHP 8.2+ with PDO SQLite and cURL is available. We verified the service with PHP 8.3 on Ubuntu/WSL. | No PHP framework or Composer runtime package is required. Windows/macOS compatibility and production PHP-FPM configuration were not exercised here. | Syntax, domain, integration and wire tests on the documented runtime. |
| A24 | Credentials are service-account environment/private-INI configuration, not request data or source. | Tokens need least-privilege scopes, rotation and a deployment secret mechanism before a pilot. No complete secret-manager integration is included. | `.gitignore`, fixed API hosts, no redirects, token/header validation, sanitized logs/errors. |
| A25 | GitHub.com and ordinary Zendesk Support tenant API hosts are the required platforms. | Enterprise GitHub hosts, proxies with rewritten paths and arbitrary custom API bases are unsupported. | Adapter constructors and HTTPS host allowlist. |
| A26 | Account permissions, Zendesk required fields/triggers/custom statuses and vendor behavior match the documented API contracts. | Offline doubles cannot establish this. A trigger can reject or transform a valid-looking update. | Real adapters exist; live sandbox account validation remains outstanding. |
| A27 | The state directory can contain sensitive title snapshots and audit history. | Storage is not encrypted by application code; audit retention is unbounded and requires an operational policy. | Restrictive CLI/router umask; private local paths; deployment encryption/retention are operator responsibilities. |

## Operator API and Swagger

| ID | Assumption or explicit decision | Why it matters; consequence if wrong | Validation or enforcement |
| --- | --- | --- | --- |
| A28 | The HTTP API serves one trusted operator/service identity, not multiple customers or roles. | A shared bearer token is insufficient for public/multi-user authorization or nonrepudiation. Per-user RBAC and tenant isolation are not implemented. | All `/api` routes authenticate before constructing application state; no cookie sessions or CORS opt-in. |
| A29 | Development HTTP is accessible only on host loopback. Native PHP binds directly to loopback; the Compose API binds inside its container and publishes a loopback host port. | It is not a production server. A real deployment needs an appropriate server, TLS, trusted proxy configuration and ingress controls. Other members of the same Compose network can reach the container API but still need the correct credential. | Router allowlist and explicit `127.0.0.1` host-port bindings. |
| A30 | API JSON bodies can be limited to 16 KiB, and list pages to 100 items. | Larger payloads are rejected. Pagination bounds response size but the repository currently enumerates all pairs before slicing. | Strict content-type/object/string-field validation and bounded query parameters. |
| A31 | `POST /api/sync` is synchronous and HTTP 200 means the sweep completed, even if pair outcomes include conflicts/dead work. | A client timeout does not mean the worker stopped. Clients must inspect state, not assume no effects or replay a source choice blindly. | Shared engine, persistent plans, worker lock and published response schema. |
| A32 | Health is public liveness; documentation/specification are public static descriptions without account data. | Health does not test providers, SQLite readiness or monitoring delivery. Authenticated inspection intentionally reveals snapshots. | Dedicated handler and no-context health test. |
| A33 | Swagger is documentation only in this slice. | Try it out is disabled; clients use the documented curl commands or another API client. Swagger cannot itself trigger a live sweep. | Vendored assets; remote validator disabled; read-only initializer; CSP. |
| A34 | A reverse proxy would provide rate limiting and shared ingress protections in a real deployment. | The prototype has no request-rate limiter, async job queue or per-client quotas. Authentication alone does not provide capacity protection. | Known limitation; never expose the demo server publicly. |

## Prometheus/Grafana, tools and AI

| ID | Assumption or explicit decision | Why it matters; consequence if wrong | Validation or enforcement |
| --- | --- | --- | --- |
| A35 | Prometheus and Grafana run locally and scrape one deployment using a dedicated read-only token different from the operator token. | No cloud account, ingest license or region is required. Shared/public monitoring infrastructure needs its own access and retention policies. | Pinned setup, provisioned dashboard/data source and local scrape/query verification; no public service exposure. |
| A36 | Aggregate fixed-label counters, latency histograms and state gauges are sufficient for this prototype. | No title text, IDs, raw errors or tokens are labels. | A37 | Telemetry must not determine business correctness, and metric observations need not be exactly once. | A telemetry-store failure cannot discard a business write plan. | A38 | REA is a local reverse-engineering aid for supported artifacts, not a PHP code-quality checker. | Its Swagger JavaScript analysis had explicitly partial semantic coverage and a vendor-bundle heap limit. It is not a complete security audit. | Actual direct MCP tool execution and retained evidence in `TOOLING-INSTALLATION.md`. |
| A39 | Agency Agents profiles are review guidance, not independent proof. | Their generic SLA, scale and coverage examples do not become customer requirements or measured results. | Review notes identify specific changes and actual tests; no persona readiness score. |
| A40 | We use AI to assist development while retaining responsibility for the design, code and documentation. | Generated reasoning can be wrong. Runtime AI does not adjudicate conflicts, grant approval or establish compliance. | README AI-use disclosure, deterministic tests, explicit operator decisions and recorded verification evidence. |
| A41 | The CLI, operator API, Swagger and monitoring share a small framework-free core. | Extra operational surfaces increase maintenance, but must not duplicate or override business rules. | Shared application composition, strict API contracts, offline tests and separate observability storage. |

## Workflow governance and rollout

| ID | Assumption or explicit decision | Why it matters; consequence if wrong | Validation or enforcement |
| --- | --- | --- | --- |
| A42 | We use a headless, deterministic workflow with narrow provider capabilities. | The service does not provide a general agent harness, arbitrary tool execution, MCP/A2A server, marketplace or semantic memory. | Shared CLI/API engine, fixed provider contracts and workflow decisions in `GOVERNANCE.md`. |
| A43 | Title-only transfer is permitted by the explicit link's opt-in; every planned outbound open/closed transition requires approval of the complete plan. | This is a prototype risk boundary, not a customer-approved compliance policy. Titles may be sensitive; a customer may require approval for all writes or forbid the transfer entirely. | Fixed `GovernancePolicy` field allowlist and `escalation-state-v1`; validate with the customer policy owner before live traffic. |
| A44 | An explicit operator attestation over the exact pair, target, preimages, versions and policy version is useful review evidence. | Approval adds latency, does not prove policy satisfaction, and must not carry to a changed plan. No expiry, revocation or rejection workflow is implemented; unchanged evidence/policy can remain authorized. Scripted demo approval is synthetic behavior, not human review. | Hash, rationale, approval audit, fresh provider reads and execution guards; stale choices quarantine and require new review. Validate approval lifetime and cancellation requirements with the customer. |
| A45 | The prototype continues using one shared operator principal. | It cannot establish human origin, individual accountability, distinct approvers, scoped agent credentials or separation of duties. An agent must not be given this credential; a future integration needs a restricted facade and per-user authorization. | No caller-supplied actor/AI override; documented read-only skill contract is guidance, not server-enforced RBAC. |
| A46 | Never rely on AI in compliance: customer obligations and control approval remain with accountable people. | AI explanations, confidence and generated rationales cannot authorize effects or demonstrate compliance. Deterministic software also does not decide whether all customer obligations are fulfilled. | No runtime LLM; code-enforced eligibility/freshness/approval and explicit control limitations. Human-owned policy discovery remains outstanding. |
| A47 | Rollout proceeds through synthetic checks, sandbox validation and a bounded live pilot with named operating owners. | We have not completed a customer rollout or established business outcomes. Each phase needs explicit acceptance criteria, data permissions and recovery ownership. | Proposed phases, responsibility matrix and pilot measures in `GOVERNANCE.md`. |
| A48 | Upgrading existing local state to add approval evidence and one telemetry series is required. | Pending plans must survive and receive the new gate; historical counters must not reset or silently heal missing rows. General migration, rollback and disaster recovery remain incomplete. | Transactional additive approval-column migration and exact validated telemetry v1→v2 migration; legacy/corruption tests. |

## Containers and local operation

| ID | Assumption or explicit decision | Why it matters; consequence if wrong | Validation or enforcement |
| --- | --- | --- | --- |
| A49 | We use Docker Engine with Linux containers and Compose for the complete local stack. | Docker Desktop must expose a working Linux engine to the shell. Host PHP, Node and Python are optional for native workflows. | Digest-pinned image builds and actual Compose startup; `docs/DOCKER.md` documents the shell/runtime boundary. |
| A50 | Default Compose operation uses synthetic local providers only, regardless of ambient host environment. | Container startup must not silently enable vendor synchronization. Live accounts need separately reviewed deployment configuration and sandbox validation. The bridge permits outbound connections; local mode is the application boundary, not an egress firewall. | Hardcoded local mode, loopback host ports, idempotent local initializer and no provider credentials in default services. |
| A51 | API, worker and operator tooling share one local application volume and the same UID/lock. | This is single-host coordination. Multiple workers/hosts or network storage are unsupported; rebuilds and normal shutdown must preserve pending intent and approvals. | Named application volume, UID10001 and the existing canonical process lock; explicit one-worker topology. |
| A52 | We generate operator, scrape and Grafana credentials into separate named volumes. | This avoids image/build-argument/Compose-environment secrets, but is not encrypted Docker Secrets or per-user authorization. Docker administrators retain access. Rotation and backup policies are unfinished. | Initializer validates and preserves existing credentials; consumers receive only their required read-only volumes. |
| A53 | Runtime code is image-owned and read-only; only state volumes and temporary filesystems are writable. | Containerization narrows accidental writes but does not establish isolation from Docker administrators or production readiness. Image pins need deliberate review and updates. | Non-root users, dropped capabilities, no-new-privileges, no host-source or Docker-socket mounts and a restricted build context. |
| A54 | Container verification uses isolated synthetic state; stack smoke checks are read-only. | Passing them does not demonstrate live vendor behavior, human approval, policy satisfaction, load capacity or notification delivery. | Containerized PHP/OpenAPI gate plus actual service-network, scrape and Grafana checks. |
